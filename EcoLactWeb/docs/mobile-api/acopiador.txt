Sí. Para el **ACOPIADOR** el diseño debe ser mucho más operativo que el de Administrador o Proveedor. Este usuario estará en campo, probablemente con conectividad irregular, por lo que la app debe permitirle hacer su trabajo con **muy pocos pasos**.

Su misión principal es:

**identificar proveedor → registrar litros → confirmar entrega → continuar con el siguiente proveedor.**

Todo lo demás es secundario.

# Estructura principal — ACOPIADOR

La navegación inferior la dejaría con solo cuatro opciones:

```text
INICIO · REGISTRAR · ENTREGAS · MÁS
```

`REGISTRAR` sería visualmente la acción principal, incluso podría tener un botón central más destacado.

```text
┌────────┬────────────┬──────────┬──────┐
│ Inicio │ + Registrar│ Entregas │ Más  │
└────────┴────────────┴──────────┴──────┘
```

Globalmente:

```text
● Online / Offline
↻ Sincronización
🔔 Notificaciones
👤 Perfil
```

---

# 1. INICIO

La pregunta que debe responder esta pantalla es:

> **“¿Cómo va mi jornada de acopio?”**

No necesita KPIs administrativos ni gráficos complicados.

### Cabecera

```text
Buenos días, Carlos

Acopiador · Zona Huata

● En línea                       🔔
```

Cuando esté sin cobertura:

```text
● Sin conexión · 3 pendientes

Tus registros se guardarán
en este dispositivo.
```

Esto es importante: **estar sin internet no debe parecer un error**.

---

## Resumen de la jornada

Solo tres datos:

```text
HOY

┌────────────────┐ ┌────────────────┐
│ 🥛 428.5 L     │ │ 🚚 14         │

└────────────────┘ └────────────────┘

┌─────────────────────────────────┐
│ ↻ 3 registros pendientes        │
│ de sincronización               │
└─────────────────────────────────┘
```

No mostraría información que no tenga relación directa con su jornada.

---

```text
│                                 │
│   QR o DNI del proveedor        │
│                                 │
└─────────────────────────────────┘
```

Esa debería ser prácticamente la acción dominante de la aplicación.

Esto ya cumple esa función.

# 2. REGISTRAR ENTREGA

Esta es **la pantalla más importante de todo el rol Acopiador**.

Debe ser extremadamente rápida.

Yo la convertiría en un flujo de **3 pasos**.

```text
Identificar → Cantidad → Confirmar
```

Nada más.

---

# PASO 1 — Identificar proveedor

La primera pantalla:

```text
REGISTRAR ENTREGA

Identifique al proveedor

┌─────────────────────────────────┐
│                                 │
│          📷 Escanear QR         │
│                                 │
└─────────────────────────────────┘

               o

┌─────────────────────────────────┐
│ 🔍 Ingresar DNI                 │
└─────────────────────────────────┘
```

No debería pedir:

* zona;
* nombre;
* código;
* dirección;

manualmente.

La aplicación ya sabe la zona del Acopiador y obtiene los datos del proveedor.

---

## Escaneo QR

Al tocar:

```text
┌──────────────────────────────┐

│      dentro del marco        │
```

# PASO 2 — Registrar cantidad

Después de identificarlo:

```text
← Registrar entrega

Juan Quispe Mamani
Zona Huata

CANTIDAD DE LECHE

        [ 32.5 ]

          Litros
```

El campo de litros debe ser enorme porque es el dato principal.

Después:

```text
Observación
Opcional

[ Escriba una observación... ]
```

Nada más.

Datos como:

* fecha;
* hora;
* acopiador;
* zona;

los registra automáticamente el sistema.

Esto elimina errores y pasos innecesarios.

# 3. ENTREGA REGISTRADA

Después de confirmar no debería mandar al usuario a otra pantalla compleja.

Debe aparecer:

```text
✓ ENTREGA REGISTRADA

32.5 L

Juan Quispe Mamani

Guardada correctamente.

● Sin conexión
Se sincronizará automáticamente
cuando vuelva la conexión.
```

Y dos opciones:

```text
[ + Registrar otra entrega ]

      Ver detalle
```

La principal es:

**Registrar otra entrega.**

Porque probablemente hay más proveedores esperando.

---

# 4. ENTREGA PENDIENTE DE SINCRONIZACIÓN


El acopiador **no debería tener que volver a registrar nada**.

# 7. ¿Puede editar una entrega?

Aquí aplicaría una regla importante.

### Mientras esté pendiente localmente

Si todavía **no se sincronizó**:

```text
🟡 Pendiente de sincronización

Editar entrega
Eliminar registro
```

Esto permite corregir un error inmediatamente.

Por ejemplo:

```text
32.5 L
```

cuando realmente eran:

```text
35.2 L
```

---

### Una vez sincronizada

Ya no ofrecería:

**Editar**

directamente.

Mostraría:

```text
✓ Sincronizada

Esta entrega ya fue enviada al sistema.
```

Si posteriormente necesitas manejar correcciones, debería existir un proceso controlado y auditable, no sobrescribir silenciosamente una entrega.

Nunca perder el registro local.

# Estructura definitiva del ACOPIADOR

Yo dejaría oficialmente este mapa:

```text
ACOPIADOR
│
├── INICIO
│   ├── Resumen de jornada
│   ├── Litros del día
│   ├── Entregas del día
│   ├── Pendientes de sincronización
│   └── Últimas entregas
│
├── REGISTRAR
│   ├── Identificar proveedor
│   │   ├── QR
│   │   └── DNI
│   │
│   ├── Registrar litros
│   ├── Observación opcional
│   ├── Confirmar
│   └── Guardar / sincronizar
│
├── ENTREGAS
│   ├── Mis entregas
│   ├── Filtros
│   └── Detalle de entrega
│
└── MÁS
    ├── Proveedores de mi zona
    ├── Comunicados
    ├── Notificaciones
    ├── Sincronización
    └── Mi perfil
```

### Navegación inferior

```text
┌────────┬────────────┬──────────┬───────┐
│ Inicio │ + Registrar│ Entregas │  Más  │
└────────┴────────────┴──────────┴───────┘
```

Para este rol hay una regla de UX especialmente importante: **el Acopiador no debería perder tiempo administrando datos**. La app debe conseguir que pueda registrar una entrega correctamente en segundos, incluso sin internet, y continuar inmediatamente con el siguiente proveedor.

Ese sería el diseño base oficial del **rol ACOPIADOR**.

---
NOTA DE LA IMPLEMENTACIÓN REAL (ver acopiador.md en esta misma carpeta):
- "Editar entrega mientras esté pendiente" (sección 7) es un concepto 100% local en SQLite: el backend no tiene PATCH/DELETE de entregas para este rol. Una vez sincronizada, no hay forma de editarla desde la app — coincide con lo que ya proponía este mismo diseño.
- El escaneo QR resuelve directamente contra el backend (no hay un paso de "búsqueda" separado): identificación + registro es una sola llamada. Ver acopiador.md para el contrato exacto.
- No hay clave de idempotencia en el backend para evitar duplicados si se reintenta un envío — ver la advertencia de offline en acopiador.md antes de diseñar la cola de sincronización.
