Sí. Para **VENTAS** la app debe estar centrada en un flujo muy concreto:

**seleccionar comprador → agregar productos → validar stock y precio → confirmar venta → descontar stock automáticamente → continuar con la siguiente venta.**

No debería convertirse en un mini-ERP con demasiadas pantallas.

# Estructura principal — VENTAS

La navegación inferior la dejaría así:

```text
INICIO · VENDER · VENTAS · MÁS
```

Y globalmente:

```text
● Online / Offline
↻ Sincronización
🔔 Notificaciones
👤 Perfil
```

`VENDER` sería la acción principal del rol, igual que `Registrar` para Acopiador.

# 9. Precio automático

Esto es importante.

El usuario **no debería escribir el precio manualmente en cada venta**.

El sistema obtiene el precio vigente según el producto y, si aplica, según el tipo de comprador.

Por ejemplo:

```text
Queso Fresco

Precio aplicado
S/ 8.00

Precio mayorista
```

Si el comprador fuera minorista:

```text
Precio aplicado
S/ 8.50

Precio minorista
```

Esto reduce errores.

# 25. Ventas offline

El rol Ventas sí debería poder registrar ventas offline, pero aquí hay un punto más delicado que con Acopio:

**el stock puede cambiar en otros dispositivos.**

La app utilizará el último stock sincronizado disponible.

Ejemplo:

```text
● Sin conexión

Stock local
Queso Fresco: 20 und.
```

El vendedor registra:

```text
-5 und.
```

La app local queda:

```text
15 und. disponibles localmente
```

Pero en el servidor podría haber ocurrido otra venta.

Por eso tenemos que manejar conflictos al sincronizar.

---

# 30. Una venta debe sincronizarse como una sola operación

Muy importante:

```text
VENTA
│
├── comprador
├── detalle productos
├── precios aplicados
├── total
└── movimientos de stock
```

Desde la perspectiva del negocio debe ser una transacción.

No queremos:

```text
✓ venta registrada
✓ Queso descontado
✗ Yogurt no descontado
```

Eso dejaría inventario inconsistente.

Ejemplo:

La app guardó offline:

```text

5 unidades
```

Pero al sincronizar el servidor dice:

```text
Stock real:
3
```

La app no debería simplemente convertir el stock en negativo sin control.

Mostraría:

```text

Queso Fresco

Solicitado
5

Disponible en servidor
3

La venta no pudo confirmarse
automáticamente.
```

Esto iría a una cola de incidencias.

Es especialmente importante en Ventas porque varios vendedores podrían trabajar simultáneamente.

# Estructura definitiva — VENTAS

Yo la dejaría oficialmente así:

```text
VENTAS
│
├── INICIO
│   ├── Ventas del día
│   ├── Operaciones
│   ├── Productos vendidos
│   ├── Alertas de stock
│   └── Últimas ventas
│
├── VENDER
│   ├── Seleccionar comprador
│   ├── Seleccionar productos
│   ├── Precio automático
│   ├── Validar stock
│   ├── Revisar venta
│   └── Confirmar
│
├── VENTAS
│   ├── Mis ventas
│   ├── Filtros
│   └── Detalle de venta
│
└── MÁS
    ├── Productos
    ├── Compradores
    ├── Comunicados
    ├── Notificaciones
    ├── Sincronización
    └── Mi perfil
```

### Navegación inferior definitiva

```text
┌────────┬──────────┬────────┬───────┐
│ Inicio │ + Vender │ Ventas │  Más  │
└────────┴──────────┴────────┴───────┘
```

La regla central para este rol sería:

**Ventas registra una sola vez la operación comercial; el sistema obtiene el precio vigente, valida el stock y genera automáticamente la salida de inventario.**

Eso mantiene la app rápida, evita registros duplicados y separa correctamente las responsabilidades entre **Ventas** y **Encargado de Planta**.

NOTA DE LA IMPLEMENTACIÓN REAL (ver ventas.md en esta misma carpeta):
- El "CARRITO · 5 productos" (secciones 8-14) NO es una sola operación atómica en el backend: cada producto se registra con una llamada independiente. Hay que rediseñar el carrito como N llamadas agrupadas en el cliente, sin garantía de todo-o-nada.
- Falta un campo "forma de pago" (CONTADO o DESCUENTO_PLANILLA) en el paso Resumen/Confirmar — el backend lo exige siempre y este diseño nunca lo pide.
- "Minorista" (secciones 6, 19, 20) en el backend real se llama "PUBLICO".
- El comprador del paso 1 puede ser también un proveedor (pagando con cargo a su próxima liquidación) — agregar esa fuente de búsqueda, no solo compradores externos.
- "🔴 STOCK BAJO" (secciones 3, 18, 19, 24) NO tiene umbral guardado en el backend — no existe stock_minimo para productos. Lo único real y disponible es "agotado" (stock = 0), que es distinto: rotúlalo así, no como "stock bajo".
- "Comunicados" (sección 23) NO tiene endpoint para este rol — ni siquiera el panel web se lo da a Ventas.
